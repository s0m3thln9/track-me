# track-me — Техническое задание

> Статус: v0.1 (черновик). ТЗ — живой документ: меняй его через PR с коммитом `docs(spec): ...`.

## 1. Цели и границы

### 1.1. Цель продукта
Менеджер задач для небольших команд (упрощённый Jira/Linear): проекты-доски, задачи со статусами и приоритетами, назначение исполнителей, комментарии, роли в проекте.

### 1.2. Учебная цель
Production-like backend на Node.js + полный цикл поставки: БД → auth → тесты → Docker → CI/CD → «сервер» → мониторинг. Каждое решение должно быть объяснимо на собеседовании.

### 1.3. MVP (v1.0) — входит
- Регистрация, вход, выход, управление сессиями (выйти со всех устройств).
- Профиль: имя, аватар по URL (без загрузки файлов), смена пароля; настройки (тема, часовой пояс).
- Проекты: CRUD, ключ проекта (`TM`), архивирование.
- Участники проекта и роли: `owner`, `admin`, `member`, `viewer`. Добавление существующего пользователя по email.
- Статусы (колонки доски) настраиваются в каждом проекте, порядок задаётся пользователем.
- Задачи: CRUD, человекочитаемый ключ (`TM-42`), статус, приоритет, исполнитель, автор, дедлайн, порядок внутри колонки.
- Список задач: фильтры (статус, исполнитель, приоритет), сортировка, пагинация, поиск по заголовку (`ILIKE`).
- Комментарии к задачам: создание, редактирование и удаление своих.
- Журнал активности задачи (audit log): кто, что и когда поменял.
- API-документация (OpenAPI), health-эндпоинты.

### 1.4. Следующие версии
| Версия | Фичи | Чему научит |
|---|---|---|
| v1.1 | Метки (labels), подзадачи, @mentions | many-to-many, рекурсивные связи |
| v1.2 | Email-уведомления, инвайты по ссылке, сброс пароля | очереди и фоновые задачи (BullMQ + Redis), Mailpit, одноразовые токены |
| v1.3 | Вложения | S3-совместимое хранилище (MinIO), presigned URLs, стриминг |
| v1.4 | Real-time обновления доски | WebSocket/SSE, pub/sub через Redis |
| v1.5 | Полнотекстовый поиск | Postgres FTS (`tsvector`, GIN-индексы) |
| v2.0 | Организации/workspaces, OAuth (GitHub) | multi-tenancy, OAuth 2.0 + PKCE |

### 1.5. Вне scope
Мобильное приложение, биллинг, интеграции с внешними сервисами, спринты и отчёты.

## 2. Роли и пользовательские сценарии

### 2.1. Роли
- **Гость** — не авторизован. Может только зарегистрироваться или войти.
- **Пользователь** — авторизован. Может создавать проекты; в чужих проектах прав не имеет, пока его не добавят.
- **Роли внутри проекта** (права даются на уровне проекта, глобальных ролей в MVP нет):

| Действие | viewer | member | admin | owner |
|---|:-:|:-:|:-:|:-:|
| Смотреть проект, задачи, комментарии | ✅ | ✅ | ✅ | ✅ |
| Создавать и редактировать задачи, комментировать | — | ✅ | ✅ | ✅ |
| Удалять чужие задачи и комментарии | — | — | ✅ | ✅ |
| Управлять статусами (колонками) | — | — | ✅ | ✅ |
| Добавлять и удалять участников, менять роли (кроме owner) | — | — | ✅ | ✅ |
| Переименовать, архивировать или удалить проект, передать владение | — | — | — | ✅ |

> Подумай сам: что должно произойти с задачами, если исполнителя удалили из проекта? Может ли admin понизить другого admin? Запиши решения в этот раздел.

### 2.2. User stories (MVP)
**Аккаунт**
- US-01. Как гость, я хочу зарегистрироваться по email и паролю, чтобы получить аккаунт.
- US-02. Как пользователь, я хочу войти и остаться в системе после перезагрузки браузера.
- US-03. Как пользователь, я хочу видеть активные сессии и завершить их все, если потерял ноутбук.
- US-04. Как пользователь, я хочу изменить имя, аватар, тему и сменить пароль (с вводом текущего).

**Проекты**
- US-10. Как пользователь, я хочу создать проект и автоматически стать его owner.
- US-11. Как owner/admin, я хочу добавить коллегу по email и выдать ему роль.
- US-12. Как участник, я хочу видеть список своих проектов.
- US-13. Как owner, я хочу архивировать проект, чтобы скрыть его без потери данных.

**Задачи**
- US-20. Как member, я хочу создать задачу и сразу получить ключ вида `TM-42`.
- US-21. Как member, я хочу перетащить задачу в другую колонку или поменять её место в колонке.
- US-22. Как member, я хочу назначить исполнителя (только из участников проекта).
- US-23. Как участник, я хочу отфильтровать задачи «назначенные на меня, приоритет high».
- US-24. Как участник, я хочу видеть историю изменений задачи.

**Комментарии**
- US-30. Как member, я хочу комментировать задачу и редактировать свои комментарии.
- US-31. Как admin, я хочу удалить неуместный комментарий.

## 3. Функциональные требования по модулям

### 3.1. Auth
- Регистрация: email уникален без учёта регистра; пароль от 8 символов, проверяется по списку утёкших паролей (опционально, HIBP k-anonymity).
- Пароли хранятся только как хэш (argon2id).
- Вход создаёт серверную сессию; клиент получает cookie `HttpOnly`, `Secure`, `SameSite=Lax`.
- Сессия имеет срок жизни (sliding expiration) и отзывается при выходе или смене пароля.
- Rate limiting на вход и регистрацию; ответ не раскрывает, существует ли email.

### 3.2. Users / Profile
- Получение и обновление своего профиля и настроек.
- Публичное представление пользователя (id, имя, аватар) без email, кроме случаев, где email нужен.

### 3.3. Projects & Members
- Ключ проекта: 2–10 латинских заглавных букв, уникален.
- В проекте ровно один owner. Передача владения — отдельная операция.
- Удаление проекта — soft delete или архив. Нужно решить и обосновать.

### 3.4. Statuses (колонки)
- При создании проекта создаются дефолтные статусы: `To Do`, `In Progress`, `Done`.
- У статуса есть категория (`todo` / `in_progress` / `done`), чтобы считать задачу закрытой независимо от названия.
- Нельзя удалить статус, в котором есть задачи (или нужен перенос задач).

### 3.5. Tasks
- Номер задачи уникален в проекте и монотонно растёт. Конкурентные создания не должны порождать дубликаты (тема: транзакции и блокировки).
- Приоритет: `none | low | medium | high | urgent`.
- Исполнитель должен быть участником проекта.
- Порядок в колонке хранится так, чтобы перемещение не требовало переписывать все строки.
- Каждое изменение полей пишет запись в activity log в той же транзакции.

### 3.6. Comments
- Markdown-текст, ограничение длины. Редактирование ставит флаг `edited`.

### 3.7. Общие требования к API
- REST, JSON, версия в пути: `/api/v1`.
- Единый формат ошибок: **RFC 9457 Problem Details**.
- Пагинация списков: cursor-based для задач и комментариев.
- Все входные данные валидируются по схеме; схема же генерирует OpenAPI.

## 4. Нефункциональные требования

### 4.1. Безопасность (ориентир — OWASP Top 10 и ASVS L1)
- Проверка авторизации на **каждом** эндпоинте по ресурсу (защита от IDOR: `GET /tasks/:id` чужого проекта → 404, а не 403. Почему?).
- CSRF-защита для cookie-аутентификации.
- Security headers (`@fastify/helmet`), строгий CORS (allowlist).
- Секреты только через env; `.env` не коммитится; конфиг валидируется при старте (fail fast).
- Никаких stack trace и SQL-ошибок в ответах в production.
- Зависимости сканируются в CI (`npm audit` / Dependabot).
- Контейнеры запускаются от non-root пользователя.

### 4.2. Производительность
- p95 < 200 мс для типовых запросов на локальном стенде при 50 RPS.
- Нет N+1 запросов в списках; индексы под все фильтры (проверяется через `EXPLAIN ANALYZE`).
- Лимит размера тела запроса; лимит `pageSize` (макс. 100).
- Пул соединений к БД с настроенным размером.

### 4.3. Логирование и наблюдаемость
- Структурированные JSON-логи (pino), уровни, `requestId` в каждом логе и в заголовке ответа.
- Пароли, токены и cookie редактируются (redact) в логах.
- Health-эндпоинты: `/health/live`, `/health/ready` (проверяет БД).
- Метрики в формате Prometheus: RPS, latency histogram, ошибки, пул БД.
- Graceful shutdown: по SIGTERM дождаться активных запросов и закрыть пул.

### 4.4. Тестирование
- Unit — бизнес-логика (права, вычисление порядка, валидация).
- Integration — каждый эндпоинт против реального Postgres (Testcontainers), включая матрицу прав «роль × действие».
- Покрытие: ≥ 80% для `modules/*/service`; падение покрытия ломает CI.
- E2E (Playwright) — 3–5 критических сценариев: регистрация → проект → задача → комментарий.

### 4.5. Качество кода и процесс
- TypeScript `strict`, ESLint, Prettier, без `any` без комментария-обоснования.
- Conventional Commits (проверяется commitlint), PR-флоу даже в соло-проекте.
- FSD на фронтенде, модульная архитектура на бэкенде (см. `04-conventions.md`).

## 5. Верхнеуровневая модель данных

```
User 1───* Session
User 1───1 UserSettings
User 1───* ProjectMember *───1 Project
Project 1───* Status
Project 1───* Task
Status 1───* Task
Task *───1 User (author)
Task *───0..1 User (assignee)
Task 1───* Comment *───1 User (author)
Task 1───* ActivityLog *───1 User (actor)
```

| Сущность | Суть | Вопросы, на которые ответишь на этапе БД |
|---|---|---|
| **User** | аккаунт, email, хэш пароля, профиль | Как сделать email уникальным без учёта регистра? |
| **Session** | серверная сессия, срок жизни, метаданные устройства | Хранить токен как есть или хэш? Почему? |
| **UserSettings** | тема, часовой пояс | Отдельная таблица или `jsonb` в User? |
| **Project** | ключ, название, счётчик задач, архив | Где хранить «следующий номер задачи»? |
| **ProjectMember** | связь User↔Project + роль | Какой primary key у связующей таблицы? |
| **Status** | колонка доски, порядок, категория | Как хранить порядок колонок? |
| **Task** | номер, заголовок, описание, приоритет, дедлайн, позиция | Что будет с задачами при удалении статуса или пользователя (`ON DELETE ...`)? |
| **Comment** | текст, автор, флаг edited | Soft delete или hard delete? |
| **ActivityLog** | событие: тип, старое и новое значение | Почему здесь подходит `jsonb`, а в Task — нет? |

## 6. API (уровень ресурсов), префикс `/api/v1`

| Ресурс | Эндпоинты |
|---|---|
| Auth | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/sessions`, `DELETE /auth/sessions` (все), `DELETE /auth/sessions/:id` |
| Me | `GET /me`, `PATCH /me`, `PATCH /me/settings`, `PUT /me/password` |
| Users | `GET /users/:id` (публичный профиль) |
| Projects | `GET /projects`, `POST /projects`, `GET /projects/:projectId`, `PATCH /projects/:projectId`, `DELETE /projects/:projectId`, `POST /projects/:projectId/transfer-ownership` |
| Members | `GET /projects/:projectId/members`, `POST .../members`, `PATCH .../members/:userId`, `DELETE .../members/:userId` |
| Statuses | `GET /projects/:projectId/statuses`, `POST ...`, `PATCH .../statuses/:statusId`, `DELETE .../statuses/:statusId`, `PUT .../statuses/order` |
| Tasks | `GET /projects/:projectId/tasks?status=&assignee=&priority=&q=&cursor=`, `POST /projects/:projectId/tasks`, `GET /tasks/:taskId`, `GET /projects/:projectId/tasks/by-key/:key`, `PATCH /tasks/:taskId`, `DELETE /tasks/:taskId`, `POST /tasks/:taskId/move` |
| Comments | `GET /tasks/:taskId/comments`, `POST /tasks/:taskId/comments`, `PATCH /comments/:commentId`, `DELETE /comments/:commentId` |
| Activity | `GET /tasks/:taskId/activity` |
| System | `GET /health/live`, `GET /health/ready`, `GET /metrics` (не публичный), `GET /docs` (OpenAPI UI) |

> Подумай сам: почему `move` — отдельный эндпоинт, а не `PATCH`? Почему у задач и nested-, и flat-маршруты (`/projects/:id/tasks` и `/tasks/:id`)? Ответы обсудим на этапе 2.
